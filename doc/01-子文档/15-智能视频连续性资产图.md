# 光阴砚 AEONQUILL — 智能视频连续性资产图

> **文档梗概**：说明智能视频 `VideoProductionProject schema v3` 中角色、视图、服饰、地点、首尾帧、镜头和人工复核的权威数据结构、命令边界、迁移规则与验证方式。
>
> **最后一次更新时间**：2026-09-03
>
> **对应检查点**：`VIDEO-005 / V0.7.37`

---

## 1. 目标与边界

连续性资产图解决的不是“让模型自动判定视频好坏”，而是把一部视频中必须稳定复用的事实变成可追踪对象：

- 角色身份与正面、侧面、背面等参考视图；
- 每个角色的基础服饰和场景变体；
- 地点、光线和空间方向基准；
- 质量模式镜头的首帧与尾帧；
- 每个镜头引用的角色、服饰、地点和帧；
- 人工对身份、服饰、地点、清晰度和运动质量的复核结论。

当前实现不声称存在已经校准的自动审美阈值。五维分数用于同一镜头内部的人工记录和返修定位；最终 `accept/retry` 由用户决定。`retry` 只给出相对弱项和定向重生建议，不会自动替用户批准成片。

## 2. 权威对象关系

```text
VideoProductionProject schema v3
├── characterProfiles[]                 # 人物工作会话的可读镜像
└── continuityGraph schema v1           # 连续性与审批权威
    ├── characters[]
    │   ├── viewIds[] ────────────────> views[]
    │   └── wardrobeIds[] ────────────> wardrobes[]
    ├── locations[]
    ├── shots[]
    │   ├── locationId ───────────────> locations[]
    │   ├── characterBindings[] ──────> characters[] + wardrobes[]
    │   ├── frameIds[] ───────────────> frames[]
    │   └── latestReviewId ───────────> reviews[]
    ├── frames[]
    └── reviews[]
```

`StoryProject` 仍然负责故事、角色、地点、场景和镜头的结构事实；连续性图是从它编译出来的生产事实。两者以 `storyProjectId + storyRevision` 绑定。故事发生变化时，`synchronizeVideoProductionProjectForStory()` 重建引用图，保留仍指向同一内容版本的资产，并使语义或依赖已经变化的镜头旧复核失效。

## 3. 耐久资源绑定

每个资产槽位只保存以下字段：

```ts
type ContinuityAssetBinding = {
  libraryItemId: string
  libraryVersionId: string
  contentHash: string       // 64 位小写 SHA-256
  mimeType: 'image/png' | 'image/jpeg' | 'image/webp'
  scope: 'project' | 'global-reference'
  boundAt: number
}
```

禁止把 Data URL、HTTP 临时 URL、绝对磁盘路径或任意 provenance 对象塞入连续性图。图片字节继续由 ProjectStore/资源库管理；生产正文只持久化资源条目、不可变版本和内容身份。因此重载、项目包迁移和路径改变不会破坏槽位身份，同内容的去重版本也不会无故使镜头失效。

槽位状态严格为：

1. `planned`：没有资产；
2. `ready`：已绑定明确版本，等待用户检查；
3. `approved`：用户批准该版本成为连续性基准。

绑定不会自动批准。替换或移除一个已批准版本，会重新计算所有引用它的镜头；不引用该槽位的镜头保持原结论。

## 4. 镜头指纹与状态

镜头指纹包含以下规范化事实：

- 镜头标签；
- 地点 ID、视觉描述、资产内容哈希与批准状态；
- 角色身份约束；
- 必需视图 ID、内容哈希与批准状态；
- 当前服饰 ID、描述、内容哈希与批准状态；
- 必需首尾帧 ID、内容哈希与批准状态。

指纹用于检测“复核时看到的输入”是否仍是当前输入，不是数字签名或外部信任凭据。项目校验会重新计算它；手工把镜头状态改成 `approved`、跨角色引用服饰、引用其他镜头的帧或保留过期复核都会失败关闭。

镜头状态由依赖和活跃人工结论确定：

| 状态 | 条件 |
| --- | --- |
| `blocked` | 至少一个必需资产没有批准 |
| `ready` | 必需资产均批准，尚无当前输入对应的人工结论 |
| `approved` | 当前输入对应的活跃人工结论为 `accept` |
| `retry-required` | 当前输入对应的活跃人工结论为 `retry` |

一个镜头最多只有一个活跃结论。新结论会把旧结论标记为 `superseded`；上游依赖变化也会撤销活跃结论，但保留历史记录。

## 5. 受控命令

人工界面和后续 Agent 必须共用 `VideoProductionCommand`：

| 命令 | 作用 |
| --- | --- |
| `continuity.asset.bind` | 给明确槽位绑定一个资源库不可变版本 |
| `continuity.asset.approve` | 人工批准已绑定版本 |
| `continuity.asset.unbind` | 移除版本并失效受影响镜头结论 |
| `continuity.wardrobe.assign` | 给镜头中的一个角色选择该角色自己的服饰状态 |
| `continuity.review.record` | 保存五维人工评分、备注和接受/定向重生结论 |

命令带生产项目 `baseRevision`。过期命令、未知字段、未知槽位、跨角色服饰、非图片 MIME、非 SHA 内容身份和资产未批准前的镜头复核均被拒绝。Agent 不能通过整份 JSON 替换绕过这些命令。

生产节点还有两道硬门：

- `asset-producer` 只有在全部必需角色视图、服饰、地点和质量模式首尾帧已批准后才能批准；
- `video-director` 只有在全部镜头都有当前输入对应的 `accept` 结论后才能批准。

## 6. 前端操作路径

在多智能体制片工作室中：

1. 打开“人物设定”或“素材生成”节点；
2. 在连续性资产图区选择人物视图、服饰状态、地点基准或镜头帧；
3. 点击槽位的“选择资源”；
4. 打开页面顶部资源库，选择某个图片版本并“用于智能视频”；
5. 返回槽位检查内容哈希，点击“批准”；
6. 在“H3 镜头生成”或“成片质检”节点逐镜头选择服饰、填写五维人工评分并记录接受或定向重生。

列表按资产组和每页 24 项展示，避免十分钟项目一次挂载数百张卡。390px 下五维评分改为双列，工作台不得产生页面级横向滚动。

## 7. 迁移与恢复

`VideoProductionProject` 从 schema v2 升级到 v3：

- v1 先补齐 v2 的生成/人物策略、人物档案和变更卡；
- v2 为人物档案补 `storyCharacterId`，创建连续性图，再把无法证明内容哈希和资源条目身份的旧松散资产引用降为 `planned`；
- 若迁移调用方同时持有 StoryProject，则直接编译角色、地点、镜头和帧引用；
- 节点审批、输出、事件、暂停状态和变更卡继续保留。

旧 `assetVersionId` 仅有一个不透明字符串，不能证明它属于哪个资源条目、内容哈希或项目范围，所以迁移不会伪造一个 `approved` 连续性资产。用户需从资源库重新显式绑定。SmartVideoDocument 外层仍为 schema v2，其内部 production 为 schema v3。

## 8. 验证与已知边界

`tests/video-continuity-graph.test.mjs` 覆盖：

- StoryProject 到角色/视图/服饰/地点/帧/镜头图的编译；
- 严格未知字段、路径、MIME、哈希、跨角色和状态绕过拒绝；
- 资源绑定、批准、素材节点门和人物镜像；
- 人工接受/重生、相对弱项建议与未校准声明；
- 上游变化只使受影响镜头失效；
- 改写故事时保留未变化资产；
- 分镜建立前已绑定角色资产在桥接后继续保留；
- v1/v2 到 v3 迁移。

浏览器纵切通过真实资源库图片完成槽位选择、不可变版本绑定、批准、SQLite 自动保存、页面重载恢复和 390×844 响应式检查。

当前仍有以下边界：

- 没有自动人脸/服饰/场景质量模型，也没有把人工分数校准为机器门；
- 没有批量批准或基于生成 Job 自动回填帧槽位；
- 没有完成对白、音色、字幕和音乐的连续性资产图；
- 仍需用固定 30—60 秒人物叙事样片完成盲审、返修率和真实 H3 质量门。
