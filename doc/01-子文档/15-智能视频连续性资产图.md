# 光阴砚 AEONQUILL — 智能视频连续性资产图与逐镜候选池

> 该文档隶属于[01-开发者文档.md 第 6 节](../01-开发者文档.md#6-模块实现)，用于补充智能视频连续性资源、实际视频候选、镜头复核和失效传播的可复核事实。

## 1. 目标与边界

连续性资产图把一部视频中必须稳定复用的事实变成可追踪对象：

- 角色身份与正面、侧面、背面等参考视图；
- 每个角色的基础服饰和场景变体；
- 地点、光线和空间方向基准；
- 质量模式镜头的首帧与尾帧；
- 每个镜头引用的角色、服饰、地点和帧；
- 每次真实生成或导入的视频候选；
- 人工对候选身份、服饰、地点、清晰度和运动质量的复核结论。

当前实现不声称存在已经校准的自动审美阈值。五维分数只记录用户实际看到的某个候选，最终 `accept/retry` 由用户决定；`retry` 只给出相对弱项和定向重生建议，不会自动批准成片。

## 2. 权威对象关系

```text
VideoProductionProject schema v5
├── characterProfiles[]                 # 人物工作会话的可读镜像
├── soundTimeline schema v1             # 声音与字幕审批权威
└── continuityGraph schema v2           # 连续性、视频候选与复核权威
    ├── characters[]
    │   ├── viewIds[] ────────────────> views[]
    │   └── wardrobeIds[] ────────────> wardrobes[]
    ├── locations[]
    ├── frames[]
    ├── candidates[] ─────────────────> 资源库不可变视频版本
    ├── shots[]
    │   ├── locationId ───────────────> locations[]
    │   ├── characterBindings[] ──────> characters[] + wardrobes[]
    │   ├── frameIds[] ───────────────> frames[]
    │   ├── candidateIds[] ───────────> candidates[]
    │   ├── selectedCandidateId ──────> candidates[]
    │   └── latestReviewId ───────────> reviews[]
    └── reviews[] ────────────────────> 镜头 + 当前候选 + 当前输入指纹
```

`StoryProject` 仍负责故事、角色、地点、场景和镜头结构；连续性图是由它编译的生产事实，两者以 `storyProjectId + storyRevision` 绑定。`synchronizeVideoProductionProjectForStory()` 重建引用图时保留仍可证明身份的资产、候选和历史，但输入语义或依赖变化的镜头会清空当前候选选择与活跃复核；不受影响镜头保持原状态。

## 3. 耐久资源绑定

图像槽位与视频候选分别使用严格绑定：

```ts
type ContinuityAssetBinding = {
  libraryItemId: string
  libraryVersionId: string
  contentHash: string
  mimeType: 'image/png' | 'image/jpeg' | 'image/webp'
  scope: 'project' | 'global-reference'
  boundAt: number
}

type ContinuityVideoBinding = {
  libraryItemId: string
  libraryVersionId: string
  contentHash: string
  mimeType: 'video/mp4' | 'video/webm'
  scope: 'project' | 'global-reference'
  boundAt: number
}
```

禁止把 Data URL、HTTP 临时 URL、绝对磁盘路径或任意 provenance 对象塞入连续性图。媒体字节继续由 ProjectStore/资源库管理；生产正文只保存资源条目、不可变版本和内容身份，因此重载、项目包迁移和路径改变不会破坏引用。

图像槽位状态严格为 `planned`、`ready` 或 `approved`。绑定不会自动批准；替换或移除一个已批准版本，只重新计算引用它的镜头。

## 4. 视频候选与镜头指纹

每个候选严格保存：

```ts
type ContinuityVideoCandidate = {
  id: string
  shotId: string
  attempt: number
  label: string
  source: 'comfyui-h3' | 'byok-video' | 'imported'
  generationMode: 'fast' | 'quality'
  asset: ContinuityVideoBinding
  inputFingerprint: string
  createdAt: number
}
```

候选一经登记即为不可变历史。同一资源版本、同一镜头和同一输入指纹不能重复登记；候选不能跨镜头选择。只有必需资产均已批准、`inputFingerprint` 与镜头当前指纹一致且 MIME/哈希合法的视频，才可成为新候选。登记候选不会自动选中，用户必须显式执行“设为当前”。

镜头指纹包含镜头标签、地点、角色身份约束、必需视图、当前服饰、质量模式首尾帧以及这些资产的内容哈希与批准状态。它用于证明“候选生成时看到的输入”仍是当前输入，不是数字签名或外部信任凭据。

镜头状态由依赖、当前候选和活跃复核共同推导：

| 状态 | 条件 |
| --- | --- |
| `blocked` | 至少一个必需资产没有批准 |
| `candidate-required` | 必需资产均批准，但还没有显式选择当前输入候选 |
| `ready` | 已选择当前候选，尚无针对该候选的活跃结论 |
| `approved` | 当前候选的活跃结论为 `accept` |
| `retry-required` | 当前候选的活跃结论为 `retry` |

一个镜头最多只有一个活跃结论。切换候选、新建结论或上游依赖变化会把旧结论标记为 `superseded`，但候选和复核历史继续只读保留；其他镜头不会被连带重做。

## 5. 受控命令

人工界面和 Agent 共用 `VideoProductionCommand`：

| 命令 | 作用 |
| --- | --- |
| `continuity.asset.bind` | 给明确图像槽位绑定资源库不可变版本 |
| `continuity.asset.approve` | 人工批准已绑定图像版本 |
| `continuity.asset.unbind` | 移除图像版本并局部失效 |
| `continuity.wardrobe.assign` | 给镜头角色选择该角色自己的服饰状态 |
| `continuity.candidate.register` | 给镜头登记当前输入上的不可变视频候选 |
| `continuity.candidate.select` | 显式选择该镜头的当前候选 |
| `continuity.review.record` | 给已选候选保存五维评分、备注和 `accept/retry` |

命令带生产项目 `baseRevision`。过期命令、未知字段、跨角色服饰、跨镜头候选、重复候选、非图片/视频 MIME、非 SHA-256 内容身份、过期输入指纹和未选候选复核全部失败关闭。Agent 不能用整份 JSON 替换绕过命令。

生产节点还有两道硬门：

- `asset-producer` 只有在全部必需角色视图、服饰、地点和质量模式首尾帧已批准后才能批准；
- `video-director` 只有在全部镜头都有针对当前已选候选的 `accept` 结论后才能批准。

## 6. 前端操作路径

在多智能体制片工作室中：

1. 在“人物设定”或“素材生成”节点绑定并批准人物视图、服饰、地点和镜头帧；
2. 打开“H3 镜头生成”节点，在目标镜头上启动视频 Adapter，或选择“从资源库添加候选”；
3. BYOK 视频完成后，系统用提交时冻结的镜头与输入指纹自动登记；若生成期间上游发生变化则失败关闭，不把旧结果冒充当前候选；
4. 资源库中已有的 MP4/WebM 可手动投递到当前目标镜头，来源记为 `imported`；
5. 在候选池检查尝试序号、来源、档位、哈希和“当前/过期”状态，显式点击“设为当前”；
6. 对当前候选填写五维评分并记录接受或定向重生；若选择重生，新结果成为第二个候选，历史保持可回看。

列表按资产组和每页 24 项展示。390px 下候选卡和五维评分改为单列/双列的可触达布局，不得产生页面级横向滚动。

### 6.1 本地 H3 自动回填

单镜头本地 H3 不依赖任务标题、提示词或当前选区猜测候选归属。前端只在故事执行项具有显式 `storyShotId` 映射且连续性镜头未被资产门阻塞时，冲刷当前智能视频正文并附加严格 `candidateBinding`：

```ts
type LocalVideoCandidateJobBinding = {
  schema: 'aeonquill.local-video-candidate-job'
  version: 1
  projectId: string
  documentId: string
  productionId: string
  productionRevision: number
  continuityRevision: number
  storyRevision: number
  shotId: string
  inputFingerprint: string
  generationMode: 'fast' | 'quality'
  executionItemId: string
  submissionId: string
}
```

服务端在提交前和 H3 完成后两次读取 WorkspaceStore 权威正文，逐项验证项目、文档、生产/连续性/故事修订、镜头、指纹、档位和 submission。重试建立新 Job 时只允许把绑定重定向到新 submission，并重新取当前仍有效的修订与指纹。成功输出先由 `ProjectStore.createLibraryAsset()` 复制为项目资源库不可变 MP4，provenance 保存 Job、重试谱系和上述身份；同一 Job/绑定的完成重放返回同一资源条目。

前端再以 `reconcileLocalVideoCandidateJob()` 对当前工作区、生产图和项目可见资源做最后复核，才发出 `continuity.candidate.register`。完成事件重放、页面刷新或已有候选都幂等收敛，候选仍须用户显式选择；过期、跨项目/文档/生产、错误资源、错误 provenance 或已变化输入只产生 `rejected` 回填，原始视频 Job 输出继续保留。定向重生按钮只切换到该候选所属的精确故事镜头并使执行清单重编译，其他镜头不变。

### 6.2 连续长片逐镜目标与清单

`video-chain` 不再把父级标题或最终 MP4 当成镜头候选依据。前端只为明确映射的每个执行项创建 `candidateTarget`，其中冻结项目、文档、生产/连续性/故事 revision、连续性镜头、输入指纹、生成档和故事执行项，但不携带 submission 或任何本机路径。服务端提交时核对 2—24 镜的唯一执行项、唯一连续性镜头与同一生产范围；真正派发子任务时再读取当前 WorkspaceStore 正文，以当前权威 revision 物化 `LocalVideoCandidateJobBinding`。

父 Job 保存 `aeonquill.video-chain-manifest` schema v1。每镜记录原始序号、请求摘要、执行项、目标、`planned/queued/completed/reused/failed` 状态、子 Job、前驱子 Job/输出资产、候选回填和复用来源；完成或复用一个有目标的镜头必须同时证明该子 Job 的回填为 `ready`。重试只有在请求摘要、子任务身份、输出资产、前驱谱系、当前权威目标和回填证明全部一致时复用，否则从首个不一致镜头重新生成。最终合片的 `sourceJobIds` 只从校验后的清单顺序产生，父级成片没有单镜头 binding，因此不会污染任一候选池。

## 7. 迁移与恢复

迁移链保持显式且不伪造事实：

- production v1→v2 补生成/人物策略与变更卡；
- v2→v3 创建连续性图，无法证明资源身份的松散旧引用降为 `planned`；
- v3→v4 增加声音字幕时间线；
- v4→v5 把 continuity graph v1 迁至 v2，镜头补空 `candidateIds` 与空 `selectedCandidateId`；
- graph v1 的旧复核补 `candidateId: null` 并统一转为 `superseded`，因为系统不能证明用户当时看过哪个视频；
- 必需图像资产已批准的旧镜头迁移为 `candidate-required`，其他镜头保持 `blocked`。

旧 `assetVersionId` 或旧复核不能被推断成真实候选。SmartVideoDocument 外层仍为 schema v2；其内部 production 通过完整迁移链进入 v5。候选和媒体引用也随 `.aeonquill` 的既有项目包事实链持久化，媒体字节仍由包体资产清单承载。

## 8. 验证与已知边界

`tests/video-continuity-graph.test.mjs` 与相关生产/存储/项目包测试覆盖：

- StoryProject 到角色、视图、服饰、地点、帧和镜头图的编译；
- graph v1→v2 与 production v4→v5 显式迁移，不发明候选；
- 图像资产绑定、批准与素材节点门；
- 两个视频候选的登记、显式选择、`retry`、替换和 `accept`；
- 非法 MIME、哈希、跨镜头、重复、过期候选和状态绕过拒绝；
- 上游变化只使受影响镜头的当前选择/复核失效，候选历史和其他镜头保持；
- WorkspaceStore 与项目包继续接受当前 production schema。

`tests/local-video-candidate.test.mjs` 另覆盖严格目标/绑定、未知字段、阻塞镜头、提交与完成双检、真实 ProjectStore MP4 提升、完成重放、重试第二版本、前端协调、跨项目忽略和过期输入失败关闭。`tests/video-chain-manifest.test.mjs` 覆盖顺序、重复/跨范围拒绝、状态转移、子任务与回填证明、复用谱系和篡改失败关闭。

P7 后台浏览器纵切先用两份不同的项目视频真实完成 BYOK 回填、候选 #1 选择与 `retry`、候选 #2 选择与 `accept`；V0.7.50 又在隔离 D 盘运行时直接写入两份带合法本地 H3 provenance 的项目资源和完成 Job，跨 sidecar 重启后完成候选 #3 定向 `retry`、候选 #4 替换与 `accept`，刷新保持恰好四个候选而不重复。V0.7.51 的独立 API/浏览器纵切通过回环 Comfy fixture 实际生成两段合法 MP4、形成两个项目候选、按清单顺序合片，并在模拟父级交付中断后零新增 prompt 可信复用两个子任务；逐镜清单在 1440×900 与 390×844 均可读且无横向溢出。当前全仓单元契约为 296/296，默认基线为 99 项。

当前边界：

- 没有自动人脸、服饰、场景或运动质量模型，也没有把人工分数校准为机器门；
- 当前 UI 已自动回填 BYOK、单镜头本地 H3 和连续长片各子镜头，并允许从资源库手动登记导入结果；父级成片仍明确不作为单镜候选；
- 候选池证明版本与审批语义，不证明真实 H3 画质已经达标；三类人物样片、盲审、返修率和固定 30—60 秒成片门仍未完成；
- 强制语音对齐、口型同步、多语言与商业声音听感仍属于后续 W3 质量工作。
