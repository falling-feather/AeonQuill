## 1. 当前结论

`PERF-001` 当前选择继续使用 React DOM 作为画布主渲染层，不进行全量 PixiJS/WebGL 重写。固定夹具在桌面与窄屏均通过以下门槛：

- 帧时间 P95 不高于 20ms。
- 指针事件到相机样式提交 P95 不高于 50ms。
- 总 DOM 不高于 450，画布实际挂载节点不高于 110。
- 受管图片在画布内不解码原图，视图只使用版本化缩略图或预览图。
- 页面无 warning/error，且不存在超过 32ms 的持续长帧。

该结论只覆盖当前 331 元件级别、单画布、普通图片/文字/形状交互。像素逐帧动画、上千个同时可见精灵、复杂混合模式和实时滤镜仍可能需要 PixiJS/WebGL 子场景。

## 2. 渲染与查询实现

### 2.1 空间索引和视口裁剪

`src/lib/canvasSpatialIndex.mjs` 为可见非连接线元件建立均匀网格索引：

1. 元件先按旋转后的世界坐标 AABB 登记到网格单元。
2. 相机和视口换算为世界坐标查询框，额外保留 240 屏幕像素 overscan。
3. 每次相机变化只查询与视口相交的 ID；选中节点和 `canvas-background` 始终保留。
4. 超大元件进入全局桶，避免跨越过多网格造成索引膨胀。
5. 连接线使用端点 Map 做 O(1) 查找，只在端点可见或连接线包围盒与视口相交时渲染。

空间索引随 `elements` 文档变化重建；单纯平移/缩放只更新查询，不重建索引。当前几百节点规模足够，后续若编辑中达到数万节点，再评估增量 R-tree 或分块索引。

### 2.2 高频相机和小地图

- 平移与滚轮相机变更先写入待提交引用，同一动画帧只向 React 提交最后一个状态；指针释放会强制刷新最后状态。
- 小地图不再为每个元件创建 DOM `span`，而是在一个高 DPI Canvas 上批量绘制静态缩略几何；相机框保留一个 DOM 覆盖层。
- `.canvas-world` 暴露 `data-total-elements` 与 `data-rendered-elements`，性能脚本可以验证裁剪是否真正生效。

### 2.3 图片资源分级

正式项目图片仍以 `/api/project-assets/<sha256>` 表示不可变原始资产；显示层通过查询参数请求派生缓存：

| 层级 | URL | 最大边 | 编码 | 当前用途 |
| --- | --- | ---: | --- | --- |
| 缩略图 | `?variant=thumbnail-v1` | 512px | WebP quality 72 | 普通画布节点、检查器缩略图 |
| 预览图 | `?variant=preview-v1` | 1600px | WebP quality 82 | 选中节点或屏幕投影大于 640px 的节点 |
| 原图 | 无 variant | 原尺寸 | 原格式 | 正式编辑输入、导出、哈希与版本权威 |

`server/asset-preview-service.mjs` 按源 SHA-256 与版本化 variant 懒生成缓存，同一键并发请求只运行一次 FFmpeg；生成先写临时文件，再原子改名。派生缓存不进入项目版本链，也不改变原始内容哈希；项目 GC 删除原资产时同步删除其缩略图和预览图。FFmpeg 临时不可用时服务端短缓存回退原图并返回 `x-miaohui-asset-tier: original-fallback`，不会把回退结果标记为正式缩略图。

## 3. 固定基准

运行入口：

```powershell
npm run build
npm run benchmark:canvas -- --label=perf-desktop-final --viewport=desktop --assert
npm run benchmark:canvas -- --label=perf-mobile-final --viewport=mobile --assert
```

脚本拒绝使用早于 `src/` 的陈旧 `dist`，并在报告中记录 bundle 文件名。每轮使用隔离桥接和临时项目库，先由 FFmpeg 生成一张真实 3840×2160 PNG，再由 30 个图片节点复用；另有 300 个文字/形状/便签和一个背景节点。测试执行 90 次中键平移，采集 requestAnimationFrame、指针反馈、DOM 和 Chromium Performance 指标。

最终基准环境：Windows `10.0.26200`、Edge `151.0.4129.78`、Intel Core Ultra 7 155H（22 逻辑核）、约 32GB 内存、device scale factor 1。系统 Edge 为无头模式，显示刷新节奏与真实用户显示器可能不同，因此必须同时看绝对门槛、DOM/资源事实与浏览器烟测。

| 指标 | 桌面 1440×900 | 窄屏 390×844 | 门槛 |
| --- | ---: | ---: | ---: |
| 总元件 | 331 | 331 | 固定夹具 |
| 平移后实际挂载画布元件 | 46 | 27 | ≤ 110 |
| 平移后总 DOM | 348 | 279 | ≤ 450 |
| 帧 P95 | 4.3ms | 4.3ms | ≤ 20ms |
| 最大帧 | 8.3ms | 12.4ms | 观察项 |
| 超过 32ms 的帧 | 0 | 0 | 0 |
| 指针反馈 P95 | 4.8ms | 4.4ms | ≤ 50ms |
| 受管原图解码 | 0 | 0 | 0 |
| 平移后缩略级图片 | 3 | 2 | 可见图片均分级 |

机器报告位于：

- `.runtime/qa/canvas-performance-perf-desktop-final.json`
- `.runtime/qa/canvas-performance-perf-mobile-final.json`

早期同夹具结构基线在裁剪前挂载 331 个画布节点、总 DOM 1704；空间裁剪与 Canvas 小地图后，同结构报告为 43 个画布节点、总 DOM 339。早期源文件并非真实 4K，只用于 DOM/主线程结构对照，不作为最终图片内存或 4K 解码结论。

## 4. DOM 与 GPU 子场景决策

当前保留 DOM 的原因：

1. 固定夹具已显著低于帧、反馈和 DOM 门槛，全量迁移没有当前性能证据。
2. 文本输入、选择框、按钮、可访问性和浏览器媒体控件在 DOM 中成本更低、行为更可靠。
3. 当前热点来自“离屏节点仍挂载、原图直接解码、小地图逐节点 DOM”，已经通过局部架构修复，而非渲染 API 本身失效。
4. 保持主画布 DOM 可以降低阶段 A 同时重写数据层、命令层和渲染层的风险。

以下任一条件在固定报告中连续出现，再建立 PixiJS/WebGL 子场景实验：

- 1500 个以上同时可见图片/像素精灵时帧 P95 超过 20ms。
- 交互反馈 P95 超过 50ms，且空间索引、资源分级和局部提交已确认无回归。
- 动画预览需要数百张纹理持续更新，DOM 媒体/Canvas2D 无法在目标机维持门槛。
- 产品确定需要复杂遮罩、实时着色器、粒子或批量混合模式。

届时只迁移高密度图片、像素和动画层；文本、可访问控件、选区与工具栏仍保留 DOM。渲染后端通过稳定元件投影读取同一 `CanvasDocument`，不得建立第二套项目格式。

## 5. 尚未覆盖的边界

- 30 个图片节点当前复用一个真实 4K 内容资产，用于验证内容寻址去重、缩略资源和节点裁剪；尚未覆盖 30 个互不相同的 4K 解码峰值。
- 基准覆盖平移，不包含连续缩放、旋转、多选拖动、富文本输入或视频同时播放。
- 图片派生缓存当前由桥接内单并发 FFmpeg 队列生成；正式桌面分发后应观察首次打开超大项目的预热时间，并按磁盘/CPU 数据决定是否独立 Worker。
- 产品壳的三模式切换与重型对话框生命周期已完成 30 分钟泄漏斜率门；画布内部连续缩放、旋转、多选拖动、富文本输入和多视频播放仍需按独立固定夹具扩展。

上述边界属于后续性能回归扩展，不改变本轮“保留 DOM 主画布、按证据增加 GPU 子场景”的结论。

## 6. 产品壳与模式级加载门

V0.7.53 将性能治理从画布内部扩展到产品首屏。`src/shell/lazyProductSurfaces.tsx` 统一登记七个动态入口：均衡模式、像素模式、智能视频、资源库、工作流中心、运行时设置和项目恢复。首页 `ProductApp` 只静态携带项目中心与基础壳；用户在模式卡、导航或对话框入口表达意图时可预取对应模块，真正进入时由统一 `Suspense` 壳显示加载状态。未打开的工作台与对话框不会提前挂载，也不会在首页同步解析。

样式同步分层：`src/base.css` 只承载首页与通用产品壳样式，原 `src/styles.css` 由均衡模式入口加载。动态模块网络失败、部署后旧块失效或 MIME/块文件异常由 `ModeErrorBoundary` 单独识别，界面明确说明项目仍保存在本地并提供整页重新载入；普通 React 渲染异常仍沿局部重新挂载路径恢复。

### 6.1 固定构建预算

`vite.config.ts` 输出 `.vite/manifest.json`，`scripts/validate-mode-splitting.mjs` 以 manifest 而不是易变文件名验证入口关系。预算和 V0.7.53 实测如下：

| 首页 JS | 493,305 | 525,000 |
| 首页 CSS | 59,264 | 80,000 |

| 像素模式 JS / CSS | 100,422 / 47,724 | 150,000 / 70,000 |

V0.7.52 首页 JS 基线为 1,013,060 bytes；本轮下降 51.31%，超过“至少降低 45%”的回归门。资源库、工作流中心、运行时设置和恢复点同样必须保持独立动态入口；示例大图不得重新成为首页依赖。

### 6.2 加载与失败恢复回归

`scripts/validate-mode-loading-ui.mjs` 使用 D 盘隔离桥接和后台系统 Edge：

1. 进入首页确认三模式和四类重型对话框均未提前挂载。
2. 首次请求均衡模式块时主动中断网络，确认用户能看到模块加载失败、本地项目保留说明和重新载入操作。
3. 执行整页恢复，再分别延迟资源库、工作流中心和运行时设置块，确认等待态可见且最终内容正常出现。
4. 在 1440×900 和 390×844 视口复核入口可达、加载/错误界面完整且无横向溢出。

### 6.3 V0.7.56 产品冷启动与持续内存门

`scripts/benchmark-product-performance.mjs` 与 `benchmarks/product-performance/thresholds.json` 建立稳定 `aeonquill-product-performance-v1` 报告。脚本拒绝使用早于 `src/` 的陈旧 `dist`，只启动 D 盘隔离 bridge 与后台系统 Edge；浏览器临时配置、缓存和下载目录全部位于隔离运行时。正式档固定 1440×900、7 轮冷/暖主页、每模式 7 轮首次/缓存进入，以及 30 分钟持续生命周期；烟测档保留相同内存与释放上限，仅对 3 样本延迟提供 1.5 倍机器抖动余量，不能替代正式档。

主页就绪定义为项目中心可见且“创建新项目”已完成 SQLite 同步；冷样本为新上下文并禁用 HTTP 缓存，暖样本为同一上下文重载。模式首次进入从提交“创建并进入”计时到实际工作台完成两帧提交；缓存进入使用同一已形成有效正文的项目反复回主页再深链进入。持续段按模式停留 750ms、主页停留 250ms 循环均衡/像素/智能视频，并周期性开合资源库和工作流中心；每 5 秒显式 GC 后采集 `JSHeapUsedSize`、`Nodes`、`Documents`、`JSEventListeners`，结束回主页并双 GC，再检查模式宿主与媒体元素均已卸载。

正式报告环境为 Windows `10.0.26200`、Edge `152.0.4191.53`、Intel Core Ultra 7 155H（22 逻辑核）、约 32GB 内存。结果如下：

| 路径 | P50 | P95 | 正式上限 |
| --- | ---: | ---: | ---: |
| 主页冷缓存就绪 | 1024.95ms | 1110.43ms | 3000ms |
| 主页暖缓存就绪 | 908.31ms | 916.79ms | 1500ms |
| 均衡模式首次 / 缓存 | 139.41 / 141.66ms | 142.22 / 208.51ms | 5000 / 2500ms |
| 像素模式首次 / 缓存 | 221.26 / 116.18ms | 347.17 / 120.82ms | 5000 / 2500ms |
| 智能视频首次 / 缓存 | 330.10 / 40.07ms | 351.50 / 94.07ms | 5000 / 2500ms |

30 分 0.804 秒内完成 1305 个完整循环。GC 归一化 JS heap 首尾增长 3,475,360 bytes，线性斜率 64,642.74 bytes/分钟；DOM 首尾 +5、斜率 0.01 节点/分钟，Document +0、事件监听器 +4。返回主页后 `[data-product-mode]` 和工作台媒体/画布宿主均为 0。全部 16 项正式断言通过，机器报告为 `.runtime/qa/product-performance-formal-v0756.json`。

长测在修复前稳定复现过约千次 GET 后的单次 `Failed to fetch`，界面会错误停在项目读取门。`projectApi` 现只对幂等 GET 的网络异常执行 80ms/240ms 两次退避重试；PUT/POST 不自动重放。基准主动注入一次 `connectionreset` 并确认第二/第三次读取透明恢复，随后完整 30 分钟门通过。

本结果与 V0.7.53 的动态拆包证据共同关闭 `AQ-PERF-001` 的产品壳冷启动、切模和持续内存子目标。它不测 GPU 显存，不外推到所有硬件、前台显示刷新率或正式 Tauri WebView；Tauri/跨硬件启动差异继续作为 `REL-002` 发行矩阵，而画布内部更复杂编辑仍按第 5 节独立扩展。
